# Roles — What This Team Actually Needs to Be

The original 7-agent roster in `AGENTS.md` was designed for building and maintaining a personal
*site* — Scout (added 2026-08-23) is the first agent designed for the bigger vision directly, not
retrofitted from a site-building role.
Jerry's said this project is now bigger than that: it's meant to organize his whole life going
forward — an ever-expanding system where agents act as HR, PR, therapist-adjacent support,
journalist, storyteller, staff, developer, designer, and even influencer, constantly
interacting with each other and with him to add work, create tasks, and track events.

This doc maps that fuller vision against the current roster — what's already covered, what needs
its scope stretched, and what's a genuine gap with no owner. **This is analysis, not a build** —
per this kit's own scope note in `FACTS.md`, deciding to add or reshape an agent is real
agent-creation work Jerry does deliberately (see `AGENTS.md`'s "Adding or Renaming an Agent"
section), not something this document does for him.

## Genuine gap — no current agent owns this, and one probably shouldn't be spun up casually

**Therapist.** This is the one that needs real care, not just a name and an email signature.
`JOURNAL.md` (Ryder-only) now holds a documented 2023 health crisis and a 2025 departure from a
14-year abusive marriage — real history, not hypothetical. An AI agent positioned as "therapist"
for someone with that specific history carries real responsibility: what it's actually for
(a reflective daily check-in already exists — that's Ryder's journal function — versus something
that reads as clinical mental-health support, which is a different, much higher-stakes claim),
what it explicitly is not and should say so, and what boundaries it holds (e.g., recognizing when
something needs a real professional, not an agent). This isn't a decision this document should
make unilaterally by drafting a persona — it's a question for Jerry: does he want the existing
daily-check-in function (Ryder's journal) to lean further into emotional support explicitly, with
real disclaimers, or does "therapist" mean something narrower he has a clearer picture of than
this analysis can guess at?

## What this suggests for the eventual rebuild

- The task board (`TOOLS.md`'s shared task categories) already has room to grow — `design`,
  `content`, `infra`, `qa`, `docs`, `press`, `general`, `dashboard` was the old set; something
  like `personal`/`life`/`schedule` would fit the HR-adjacent function without inventing a new
  agent first.
- `SCHEDULE.md` (new, alongside this file) is a first step toward the "organize calendar events"
  half of the vision, independent of who ends up owning it.
- Team communication (`get_team_updates`/`post_team_update` in `TOOLS.md`, and the whole
  "self-expanding, agents talk to each other and to Jerry" design goal from `FACTS.md`) is
  already the right *mechanism* for this — the gap is roles/ownership, not infrastructure.
